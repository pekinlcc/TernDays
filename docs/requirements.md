# TernDays 需求说明（v0.1 草案 · 待确认）

一个统计「一个自然年内，你在每座城市各待了多少天」的移动应用。

- 平台：Android + iOS
- 页面原型：https://claude.ai/code/artifact/aea2442a-2347-410c-aeff-b2cd92225906
- 状态：本文件为需求确认稿，「待确认」条目需产品负责人拍板后进入开发。

## 1. 核心机制：每日两次自动打卡

- 每天 **07:00** 与 **17:00** 各自动记录一次位置（下称「早点」「晚点」）。
- 定位只用 **GPS / 系统定位服务**，不用 IP（用户使用境外 SIM 卡或代理时 IP 不可靠）。
- 每次打卡仅保留：时间戳、经纬度反解出的**城市**（原始坐标是否保留，见待确认 Q5）。
- 需要「始终允许」后台定位权限；每天仅定位两次，无持续追踪。
- 已知系统约束（技术风险，开发前需原型验证）：iOS / Android 均不保证后台任务整点执行，
  实际打卡会落在目标时刻附近的时间窗内；应用需做补偿策略（延迟重试、打开应用时补取等）。

## 2. 计天算法

以「自然年」为统计周期（1月1日 – 12月31日），每天最多贡献 1 天：

| 当天记录情况 | 计法 |
| --- | --- |
| 早点、晚点在同一城市 | 该城市 +1 天 |
| 早点、晚点在两个城市 | 两城市各 +0.5 天 |
| 只有一次记录（早或晚） | **待确认**（建议：该城市 +1 天） |
| 全天无记录 | **待确认**（建议：计入「无记录」，允许手动补记） |

## 3. 页面（对应原型编号）

1. **首次启动 · 权限引导**：说明打卡机制与隐私承诺，引导授予「始终允许」定位权限。
2. **首页 · 城市天数列表**：年份切换；年初至今汇总（已记录天数 / 城市数 / 无记录天数）；
   今日早晚打卡状态；城市列表按天数降序（城市名 + 天数，含 0.5 精度）。
3. **城市详情 · 日历视图**：该城市全年累计；月历标记全天 / 半天；打卡明细列表
   （每天早晚的实际打卡时间与城市）。
4. **导出**：选择年份；格式 Excel(.xlsx) 或 CSV；内容含「城市汇总」与「每日明细」两部分；
   文件本机生成，经系统分享面板保存或发送，不经网络。

另附深色风格备选稿（低保真），供确定视觉方向。

## 4. 数据与隐私

- 所有数据仅存手机本地（SQLite 或同类），无账号、无服务器、不上传。
- 删除应用即清除全部数据（是否提供本地备份/迁移，见待确认 Q6）。
- 反地理编码（坐标 → 城市名）优先使用系统离线/系统自带能力，避免引入联网依赖（待技术验证）。

## 5. 待确认问题

| # | 问题 | 建议默认值 |
| --- | --- | --- |
| Q1 | 一天只有一次打卡记录时怎么计？ | 按该次记录城市 +1 天 |
| Q2 | 全天无记录（关机/无信号/权限被收回）怎么办？是否允许手动补记？ | 计为「无记录」，允许在应用内手动补记城市 |
| Q3 | 「城市」粒度：国内按地级市（如「杭州」）？直辖市按市？境外按城市名？ | 国内地级市/直辖市，境外取系统反解的 city 字段 |
| Q4 | 07:00 / 17:00 按手机当地时区还是固定时区？跨时区旅行日如何处理？ | 按手机当前本地时间 |
| Q5 | 是否保留原始经纬度（导出明细更精确），还是只存城市名？ | 保留坐标，仅本地存储 |
| Q6 | 是否需要本地备份/换机迁移（如导出/导入数据文件）？ | 一期不做，导出功能可兜底 |
| Q7 | 打卡时间 07:00 / 17:00 是否允许用户在设置中调整？ | 一期固定，不开放 |

## 6. 非目标（一期不做）

- 账号体系、云同步、多设备。
- 轨迹记录、地图展示。
- IP / Wi-Fi 定位兜底（仅 GPS/系统定位）。
